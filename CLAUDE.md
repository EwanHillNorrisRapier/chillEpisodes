# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Working copies of Microsoft Fabric notebooks (PySpark / Spark SQL) and Fabric warehouse T-SQL for the Chill **Episode Event Stream**: a table of customer journey events (quotes, calls, sales, renewals, chases, and so on) built from the client's data, plus the friction extract and the behavioural segmentation dataset built on top of it. Nothing here builds, lints or tests locally. Notebooks run in Fabric (kernel `synapse_pyspark`): developed in the workspace **Dev_CGP**, then promoted to UAT and prod. Every workspace has a lakehouse `ChillLH` with the same schema names. The T-SQL runs in a Fabric warehouse. There is no package manifest or test runner in this repo.

`.ipynb` files are large single-line JSON. To read one, extract the cells with node rather than reading the raw file:

```
node -e "const nb=JSON.parse(require('fs').readFileSync(process.argv[1],'utf8'));nb.cells.forEach((c,i)=>console.log('--- ['+i+'] '+c.cell_type+'\n'+[].concat(c.source).join('')))" "main_v2/02 - Episodes Build/ADS_v2_00_Setup.ipynb"
```

## Layout

- `main_v2/` is the current build (v2): one folder per Fabric pipeline, described below.
- `main/` is the legacy v1 build. `04 - Populate Episode Event Stream` appends about 300 event types into `ods.EpisodeEventStream` from dlk/edw/ods/stg/lkp with literal dates. `05 - Attach SCV ID` links events to SCV customers. v2 replaces both, plus notebook 06 (episode numbering). Use v1 for parity comparison and history, not as a pattern to copy.
- `scratchCode/`, `fabric_extract_20260923/` hold scratch work and exports of the per-journey reconciliation notebooks. The root `.xlsx` files are reconciliation and planning workbooks.
- `Claude outputs/` holds the pipeline import zips and code views (see below). It and `main/config/` also hold T-SQL for the **ops harness**, a stored procedure graph scheduler (`ops.CSP*`) being deployed into a Fabric warehouse (see the last section).

## v2 architecture (main_v2)

Data flows through these layers: `dlk` / `edw` (client source replicas) and `pii` (read only inside Fabric to make hash keys) → **`ods_v2`** (56 tables of reassembled client data, nothing derived, no personal data) → **`ads_v2`** (event stream built from `ods_v2` only, plus the SCV link `ods.scveadmlinkfinal`) → `prd`. The friction extract and the `beh` behavioural dataset are built on top of these.

**The notebooks in `main_v2` are the source of truth and are maintained by hand.** They were first generated by `C:\Workspaces\CGP_analysis` (ODS from `ods_build/v2`, ADS from `ads_build/v2`, friction and BEH from their own generators) but are no longer regenerated, so edit them here. The friction and BEH intro cells still carry their old "generated" headers.

## Pipelines and folders (main_v2)

Each folder is one Fabric pipeline: its notebooks (including the setup notebook they `%run`), the pipeline JSON (ARM export), its `- JSON code view.json` and `manifest.json`. The import zip (pipeline JSON + manifest) is built from the folder into `Claude outputs/<pipeline>.zip`, next to a copy of the code view; keep the three in step when a pipeline changes. The folders run in order, each reading the previous one's output:

- **`01 - ODS Build v2`** builds `ods_v2`. Parameters `batch_id`, `source_set`, `cutoff_date`. Dependencies: `10_Policy` → `11_Policy_Loan` and `20_Quote` → `21`–`25`, `30_Interaction`; `31_Web_Session` (`ods_v2.WebSession`, read by BEH) and `40_Reference` need nothing.
- **`02 - Episodes Build`** builds `ads_v2`. Parameters `batch_id`, `start_time`, `end_time`, `effective_date`. Dependencies: `10_Common` (shared tables: active sales, Relay documents, renewal cycles, re-quotes, HFQ prices/payments, contact / SCV links, call attribution, Motor and Home cancellations) → `11`–`17` (event families by product and journey; `18_Travel` needs nothing from 10) → `19_EventStream` → `20_ScvAttach` → `21_EpisodeNumbering` and `22_Parity`; `23_CampaignHistory` needs only 10. `19_EventStream` unions every family into `ads_v2.EventStream`, one row per `EventId`, and writes per-family output tests to `ads_v2.AdsFamilyCheck`.- **`03 - Friction Build`** builds the friction extract (spec v3.3): `01 - Policy Renewals 30d` → `02 - Friction Frame` → `03 - Friction Measures Car` → `04` Home and `05` Van → `06 - Friction Extract Assembly`, which writes `stg.friction_episode_v3` and a dated copy `ods.friction_episode_v3_<DataDate>`. No pipeline parameters and no setup notebook: settings are SQL `Set` cells at the top of each notebook, and tables are named directly (`stg.seg_*`, `stg.fe3_*`, `stg.fe3m_*`).
- **`04 - Behavioural Segmentation Build`** builds the `beh` schema (the rolling customer behaviour dataset): `BEH_10_Lifecycle` → `20_Activity` → `30_Rolling` and `40_RenewalHistory`; `50_Outcomes` after 30; `60_Dataset` after 40 and 50. Parameters `batch_id`, `last_me`, `renewal_outcome_end`, `outcome_end`, `friction_v3_table`; blank parameters fall back to the defaults in `BEH_00_Setup`, including dated ones (`last_me`, and `friction_v3_table` naming one dated friction copy) that need moving on for each new data date. Reads `ods_v2`, `ads_v2` and the friction copy.

**Pipeline conventions:**
- At most two notebooks run at once (the Fabric capacity struggles with more). Each pipeline is laid out as two lanes, each a chain, on top of the real dependencies. All dependencies are `Succeeded`, so a failure stops the rest of its lane; rerun from the failed notebook.
- Notebook activities carry no `workspaceId` (they use the pipeline's own workspace) and the placeholder `notebookId` `00000000-0000-0000-0000-000000000000`. Pick each notebook once after importing a pipeline.
- Notebook-launched orchestration (`runMultiple` / `notebook.run`) fails in Fabric (`%run` inside the child notebooks breaks), so orchestrate with pipelines only.

**Promoting to UAT / prod:** upload the `.ipynb` files; each notebook attaches `ChillLH` of its own workspace by name (cell 0, below), so no lakehouse rebinding is needed. Then import the pipeline zips and pick the notebooks.

## Notebook conventions

**Notebook pattern**, the same in every ODS and ADS build notebook (BEH follows steps 0–2; friction has cell 0 and then its `Set` cells):
0. A `%%configure -f` cell that attaches `ChillLH` by name, so the notebook binds to the lakehouse of whichever workspace it is imported into. The notebook metadata carries no lakehouse or workspace ids. The setup notebooks (`ODS_v2_00_Setup`, `ADS_v2_00_Setup`, `BEH_00_Setup`) have no configure cell: they are `%run` inside the caller's session, where `%%configure` errors.
1. A parameters cell (`batch_id`, and for ODS `source_set`).
2. `%run ODS_v2_00_Setup` / `ADS_v2_00_Setup` / `BEH_00_Setup` (BEH settings are `${beh.*}`). Setup sets Spark conf variables (`ods.target`, `ods.stg`, `ods.cutoff_date`, `ods.batch_id`, `ods.dlk`/`ods.edw`/... for ODS; `ads.target`, `ads.ods`, `ads.stg`, `ads.start_time`, `ads.end_time`, `ads.effective_date` for ADS). It also registers the hash/redact UDFs (`ods_hash_email`, `ods_hash_phone`, `ods_hash_id`, `ods_eircode_area`, `ods_redact`) and the run log helper.
3. A start log, then one SQL statement per cell. SQL refers to schemas and windows only through `${ods.*}` / `${ads.*}` substitution.
4. A final checks cell: unique non-null business key, distinct surrogate key, no PII-named columns, no email/mobile values in text. It writes to `OdsBuildLog` / `AdsBuildLog` and fails the notebook on any failure.

**House style for SQL cells:** no CTEs. Intermediate steps are their own tables (`stg.odsv2_*`, `stg.adsv2_*`, event families as `stg.adsv2_evt_<code>`). Every cell is `create or replace`, so re-running from a failed cell is always safe. **SQL cells hold no comments at all** (no `/* */`, no `--`): a comment in a cell made Spark in Fabric do a full parse of it and stall (`QuoteMotor`, November 2026). Each SQL cell's description sits in the markdown cell directly above it: the table name, Description, Grain, Business key / Surrogate key, Source, Reads, and a **Notes** list for what used to be inline comments. No literal dates: the window comes from settings only.

**Key conventions:**
- `EventId = xxhash64(code, grain, references, minute)`, stable across runs. Duplicates from a repeated source row collapse in the union.
- Every event carries `EventTimeBasis` (actual / derived) and real `SourceSystemId`s: 1 Relay, 2 MFQ, 3 HFQ, 4 Home QS, 5 Mapfre, 7 Van, 8 Travel quotes, 9 QuotationStorage, 20 Genesys, 21 Xtremepush, 22 Mercury, 23 CDA.
- Personal data only ever appears as salted SHA-256 `*Key` columns. Free text that can contain contact details goes through `ods_redact`. Names, addresses, DOB and full Eircodes are never taken. **The hash salt in the two setup notebooks must be identical and must never change**: every key depends on it.
- `source_set` switches between the `frozen` dev sources (`dlk`, `edw`, `dlk_bak_20260914`, `ods`, `pii`) and `prod` (`prod_dlk`, `prod_edw`, `prod_pii`).
- ODS event/transaction tables start at the cut-off 2021-04-01. Policy tables keep their full history.
- `ods.scveadmlinkfinal` is the **only** policy / quote / client → SCV link. References that do not link go to `ads_v2.ScvLinkExceptions`; they are never given a silent negative key.

## Writing or reviewing an event family

The v1 stream had 15 recurring failure patterns (the bugs-and-lessons write-up, 16 October 2026, no longer kept). The ones to check every time:
- Read the flow sheet text for the step, not only its name (`Chill_Episode_Frameworks.xlsx`). If it says "no signal", do not build the step.
- Do not infer what a code, channel or flag means from its values. Ask Vijay, then record the answer in the decision log (`out/e1_findings.md` in the CGP_analysis repo).
- Profile the source before joining on it. Look for `GDPR` sentinel values, unreliable flags (`RecordVersionIsLatest`: use `max(RecordVersion)`), mixed clocks (MFQ was Irish local time until 2026-06-11 and UTC after that), and keys a product does not fill (Home sales have no `QuoteQueryGuid`; use `HEQReference`).
- Anchor each event to its cycle or sale with a date range, not only to the policy or customer. Use the real event time, not a proxy such as the sale date or due − 60. Keep one event per occurrence at its first time: no `GROUP BY PolicyCode` over the whole window, and no month bucketing.
- Put only keys of the right type in reference columns: only an SCV key in the customer column, never an email or a guid.
- Watch for SQL that cannot work: `NOT IN` against a list that contains NULL, or a quoted string compared as if it were a column (use backticks).
- Before handover, check the step's output: row count against the source's own event count, zero exact duplicates, min and max time inside the window and not after the data date, and an explanation for zero rows or a count identical to another family.

## Ops harness (Fabric warehouse T-SQL)

`ops.CSP*` is a graph scheduler. A graph (`CSPScheduleGraph`) has nodes (`CSPScheduleGraphNode`) joined by segments (`CSPScheduleGraphSegment`), and each node's SQL is stored in `CSPScheduledItemString` with `##` tokens that `ops.CSPSubstituteParams` replaces. The entry point is `EXECUTE ops.CSPExecuteGenericGraph @cspgraphid = <id>`.

To deploy into a new warehouse, run these in order: `Claude outputs/Deploy harness/1 - check schemas.sql` → `2 - create tables and seed.sql` → `create_harness_trimmed.sql` → `3 - dummy graph.sql` (graph 9001, a smoke test). The order matters because the inline TVFs bind their tables at create time.

`Build EventStream graph/` defines graph 7001: 38 nodes mirroring a Fabric notebook, node ids from 7010 in steps of 10, and scheduled item id = node id. Its node SQL is still Spark SQL, so build nodes fail until that SQL is translated to T-SQL.

Fabric warehouses are **case sensitive**: schema and object names must match exactly (`ops`, `stg`, `trk`, all lower case).
